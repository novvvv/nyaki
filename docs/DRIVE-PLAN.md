# 사용자 Drive 저장 전환 (설계안)

> 단어·메모를 Hub에서 사용자 Google Drive로 옮기고, Hub는 재화·퀘스트만 담당하게 하는 구조 변경안.
> 2026-09-10 작성. 착수 확정 시 [PLANS.md](PLANS.md)로 통합하고 이 파일은 지운다.
> 현재 구조는 [ARCHITECTURE.md](ARCHITECTURE.md), 진행 상태는 [TASKS.md](TASKS.md).

---

## 1. 원칙

**사용자가 쓴 것은 사용자가 소유한다.** 단어·뜻·메모·예문은 서버를 지나가지 않는다.

이 한 줄에서 나머지가 전부 따라온다. 서버가 보관할 이유가 있는 것만 남기고,
없는 것은 사용자 Drive로 내보낸다.

| | 저장 위치 | 근거 |
|---|---|---|
| 단어 · 단어장 · 메모 · SM-2 상태 | **사용자 Drive** | 사용자 소유물. 서버 원가가 0이고 보관할 명분이 없다 |
| 츄르 · 열빙어 · 퀘스트 · 스트릭 | **Hub** | 누적값이라 서버 판정이 필요하고, 개인 정보가 아니다 |
| 인증 | Firebase | 변경 없음 |

---

## 2. 무엇이 사라지는가

### 2-1. Hub

`word_books` · `words` · `sync_changes` 세 테이블과 push/pull 경로가 빠진다.
남는 것은 `user_progress` · `quest_states` 둘뿐이다.

### 2-2. 동기화 기술부채 전체

TASKS 2절의 결함 A~G가 **원인째 소멸한다.** 고치는 게 아니라 그 코드가 없어진다.

| 결함 | 소멸 이유 |
|---|---|
| A 배치 하나가 전체를 막음 | push 자체가 없다 |
| B 삭제가 절반만 전파 | 서버가 단어를 안 가진다 |
| C `sync_changes` 무한 증가 | 로그 테이블이 없다 |
| D 부모 미확인 | `_apply_mutation`이 없다 |
| E 클라이언트 시계 신뢰 | 병합이 없다 |
| F pull N+1 | pull이 없다 |
| G cursor 정체 | cursor가 없다 |

`model_dump(exclude_unset=True)` 문제도 단어 payload가 사라지면서 함께 정리된다.

### 2-3. 웹 단어장 — 전환 시점에 결정한다

웹은 Hub REST로 단어를 읽고 썼다. 블로그를 접은 지금 웹에 남은 기능은 단어장뿐이다.

**바로 지우지 않는다.** 그림자 기간(11절 1~2단계) 동안 진실은 여전히 Hub이므로
웹은 정상 동작한다. 문제가 되는 건 **앱이 Drive를 진실로 삼는 순간**이다 —
앱에서 추가한 단어가 웹에 안 뜨고, 웹에서 추가한 단어는 앱에 안 간다.

그래서 3단계 직전에 셋 중 하나를 고른다.

| 선택 | 결과 |
|---|---|
| 읽기 전용으로 전환 | 쓰기만 막으면 갈라짐이 한 방향이라 피해가 작다 |
| 단어장 폐기 | 가장 단순. 입력은 스프레드시트가 대신한다(6절) |
| 웹에도 Drive 연동 | 웹에 Google OAuth + Drive를 새로 구현. 비용이 크다 |

**웹 단어 추가의 실질 가치는 "PC 키보드로 빠르게 넣는 것"인데, 그 역할은
스프레드시트가 대신한다.** 오히려 대량 붙여넣기가 되어 낫다. 다만 시트에서 고친 것은
중복 판정 문제로 새 단어가 될 수 있으므로, **입력은 시트 · 수정은 앱**으로 갈린다.

### 2-4. 데이터 개수 기반 과금

서버가 사용자 단어 수를 모르므로 **"Free 단어장 3개 / 단어 100개" 쿼터를 강제할 수 없다.**
클라이언트에서만 막는 건 우회 가능하므로 이 모델은 폐기한다. 9절 참고.

## 3. Drive 저장 구조

같은 Drive 안에서도 **앱이 쓰는 정본**과 **사람이 만지는 창구**를 나눈다.

```
Drive
├─ appDataFolder/
│    nyaki-backup.json        정본. 앱만 접근. SM-2 상태 포함
└─ 내 드라이브/
     냐키 단어장.gsheet         사람이 보는 창구. 내보내기 · OCR 입력함
```

### 3-1. 정본을 appDataFolder에 두는 이유

`appDataFolder`는 Drive UI에 노출되지 않는 앱 전용 영역이다.
SM-2 상태(`ease` · `interval` · `repetitions` · `lapses` · `due_at`)가 스프레드시트에
보이면 정렬 한 번, 행 삭제 한 번으로 학습 이력이 뒤섞인다. 되돌릴 방법이 없다.

서버에 두자는 것이 아니라 **같은 Drive 안에서 실수로 만질 수 없는 칸**에 넣는 것이다.
계정은 여전히 사용자 것이고 권한은 언제든 회수할 수 있다.

### 3-2. 스프레드시트는 단방향

- 앱 → 시트: 내보내기 (사람이 읽기 위해)
- 시트 → 앱: 가져오기 (손으로 추가한 단어, OCR이 채운 단어)

**양방향 자동 동기화는 하지 않는다.** 시도하면 지금 걷어내려는 문제가 그대로 돌아온다.
시트에는 SM-2 상태를 쓰지 않으며, 가져온 단어는 신규 단어로 취급한다(6절).

### 3-3. OAuth 스코프

`drive.file` — 앱이 만들거나 사용자가 선택한 파일만 접근하는 스코프.
민감 스코프가 아니라 구글 심사 부담이 가볍다.

사용자가 **이미 쓰던** 시트를 읽으려면 `spreadsheets` 또는 `drive.readonly`가 필요한데,
이건 민감 스코프라 검증 절차가 붙는다. **앱이 시트를 만들어주는 방식**으로 설계해
`drive.file` 안에서 끝낸다.

## 4. 백업 전략 — 자동이어야 한다

TASKS 8절에 Drive 백업이 P2로 잡혀 있던 근거는 **"Hub sync가 백업 역할을 해서 급하지 않음"**이었다.
그 역할을 빼는 순간 **Drive 백업이 유일한 안전망**이 된다. 우선순위가 P2에서 P0로 올라간다.

- **수동 백업은 사용자가 하지 않는다.** 안 하다가 기기를 잃으면 전손이다
- 앱 시작 시, 포그라운드 복귀 시, 변경이 있으면 조용히 올린다
- 마지막 백업 시각을 화면에 보여준다

### 4-1. 백업 실패를 반드시 노출한다

결함 A가 가르쳐준 교훈이 여기에도 그대로 적용된다.
`catch (_) {}`로 삼키면 **백업이 몇 달간 멈춰 있어도 아무도 모른다.**

- 연속 실패 카운터
- 임계치 초과 시 화면에 배너
- 마지막 성공 시각이 오래됐으면 경고

**이건 선택이 아니라 필수다.** 유일한 안전망이 무증상으로 끊기는 상황을 만들면 안 된다.

## 5. 복원과 다기기 정책

여기가 가장 위험한 구간이다.

### 5-1. 백업은 동기화가 아니다

기기 A에서 10개 추가 → 백업. 기기 B에서 5개 추가 → 여기서 복원하면?

- **덮어쓰기**: B의 5개가 사라진다
- **병합**: `updated_at` 비교와 충돌 해소가 필요하다. Hub가 하던 일을 클라이언트에서 다시 만드는 셈

### 5-2. v1 정책 — 복원은 명시적 행위로 한정

**복원은 기기 교체·재설치 시 1회.** 일상적인 다기기 동시 사용은 v1 범위에서 제외한다.

- 복원 화면에 "이 기기의 현재 데이터를 백업본으로 교체합니다"를 명시
- 복원 직전 현재 로컬 상태를 별도 파일로 백업(되돌릴 여지)
- 자동 복원은 하지 않는다. 사용자가 눌러야만 일어난다

혼자 쓰는 단어장이라는 전제에서 이 타협이 합리적이다.
다기기 실시간 동기화가 필요해지면 그때 병합을 설계한다.

### 5-3. 백업 파일 형식

```json
{
  "schema_version": 1,
  "exported_at": "2026-09-10T12:00:00Z",
  "device_id": "...",
  "word_books": [ ... ],
  "words": [ ... ]
}
```

`schema_version`을 처음부터 넣는다. 나중에 필드가 늘 때 구버전 백업을 읽어야 하는데,
버전이 없으면 추측으로 파싱하게 된다.

## 6. 스프레드시트 가져오기 · OCR

### 6-1. 가져온 단어는 신규 단어다

```
ease 2.5 · interval 0 · repetitions 0 · lapses 0 · due_at = now
```

ARCHITECTURE 1절 규칙 1번("새 단어 기본 상태: unmemorized, SRS 즉시 due")을 그대로 따른다.
**SM-2는 이 전환의 영향을 받지 않는다** — 가져오기가 하는 일은 단어를 만드는 것뿐이고,
그 뒤는 기존 채점 흐름과 동일하다.

### 6-2. 중복 방지가 진짜 어려운 부분

같은 행을 두 번 가져오면 단어가 복제되거나, 더 나쁘게는 기존 단어를 덮어써서
**학습 이력이 리셋된다.** 시트에는 안정적인 ID가 없으므로 직접 만들어야 한다.

| 방법 | 장점 | 단점 |
|---|---|---|
| 앱이 시트에 `nyaki_id` 열을 써넣는다 | 확실함 | 시트 쓰기 권한 필요 |
| `(단어장, term)` 조합으로 판정 | 쓰기 불필요 | 사용자가 오타를 고치면 새 단어로 들어옴 |

전자를 권한다. 어차피 앱이 만든 시트라 쓰기 권한이 이미 있다.

### 6-3. 외부 데이터 유입 = 검증이 필요해진다

지금까지는 앱이 만든 데이터만 들어왔다. 시트·OCR·CSV가 붙으면 **길이 초과, 빈 값,
깨진 인코딩**이 들어온다. 서버로 가지 않으므로 결함 A 같은 영구 정지는 없지만,
로컬 DB가 오염되면 그게 그대로 백업된다.

- 가져오기 단계에서 길이·필수값 검증
- 거른 행을 사용자에게 보여준다("3행: 단어가 비어 있어 건너뜀")

## 7. 퀘스트는 영향을 받지 않는다

`complete_quest`가 건드리는 테이블은 `quest_states` · `user_progress` 둘뿐이다.
**`words`를 조회하는 코드가 한 줄도 없다.** `add_word` 퀘스트도 앱의 신고를 그대로 믿는다.
즉 단어를 서버에서 빼도 잃는 것이 없다.

복습 퀘스트(G3)도 마찬가지다. 앱이 로컬에서 센 **정수 두 개**(`reviewed_count`,
`due_remaining`)만 보낸다. 단어 내용은커녕 단어 ID도 가지 않는다.

### 7-1. 자기 신고를 믿어도 되는 이유

서버는 이 숫자를 검증할 수 없다. 하지만 **하루 상한이 인플레를 막는다**(PLANS 1-1: 츄르 10 · 열빙어 2).

| | 획득 경로 | 하루 최대 |
|---|---|---|
| 성실한 사용자 | 복습 | 열빙어 2 |
| 조작하는 사용자 | 자기 신고 | 열빙어 2 (동일) |
| 결제하는 사용자 | 구매 | 즉시 원하는 만큼 |

조작해도 성실한 사용자보다 빨라지지 않는다. **판매하는 것은 시간**이므로
유료 재화(열빙어 판매)와 공존할 수 있다.

### 7-2. 그러려면 서버가 강제해야 하는 것 셋

1. **하루 상한을 서버가 센다** — 앱이 아니라. `quest_states`가 이미 "오늘 완료했나"를 들고 있다
2. **시간대 판정은 서버 수신 시각으로** — 기기 시계를 바꿔 아침 퀘스트를 여러 번 깨는 것을 막는다
3. **멱등성 유지** — 같은 날 재호출해도 한 번만 지급. 현재 `complete_quest`가 이미 그렇다

## 8. 책장 계획이 대폭 축소된다

PLANS 2-6의 7단계 중 절반이 Hub 스키마와 동기화다. 단어가 Hub에서 빠지면 **앱 로컬만의 작업**이 된다.

| | 전 | 후 |
|---|---|---|
| 1. Hub 스키마 + alembic 백필 | 필요 | **삭제** |
| 2. Hub API + 동기화 | 필요 | **삭제** |
| 2b. 배치 참조 보강 · hasMore · exclude_unset | 필요 | **삭제** |
| 3. 앱 Drift + 모델 · 저장소 | 필요 | 필요 |
| 4. 앱 동기화 (outbox · merge · bootstrap) | 필요 | **삭제** |
| 5. 앱 UI | 필요 | 필요 |
| 6. 범위 지정 (책장 단위 테스트) | 필요 | 필요 |

7단계 → 3단계. "Hub 먼저 배포", 고아 단어장, 페이지 경계 문제가 전부 사라진다.
백업 파일에 `shelf_id`를 넣고 `schema_version`을 올리는 것으로 끝난다.

## 9. 과금 모델

데이터 개수 기반 쿼터가 불가능해지므로 축을 옮긴다.

| 축 | 판단 | 근거 |
|---|---|---|
| **OCR 사용량** | 주력 | 실제 원가가 발생하고, 서버 경유라 정확히 세며, 우회가 불가능하다 |
| **열빙어 판매** | 가능 | 7-1의 하루 상한 구조에서 성립. 단 환불·이연수익·심사 부담을 감수해야 한다 |
| 광고 제거 | 조건부 | 광고 SDK는 식별자를 수집한다. 방금 가볍게 만든 개인정보 부담이 돌아온다 |
| 코스메틱 직접 판매 | 대안 | 비소모성 IAP라 잔액 관리·환불 이슈가 없다 |

### 9-1. 열빙어를 팔기로 하면 — 유상/무상 분리가 선결이다

검증(조작 방지)은 규제·심사 요건이 아니다. 무료로도 얻을 수 있는 재화를 파는 것은
대부분의 앱이 하는 일이고, Apple 3.1.1과 게임산업법이 요구하는 것은 뽑기 확률 공개
(정찰제면 무관)와 결제 경로(IAP 사용)다. 조작은 매출 문제지 위법이 아니다.

**실제로 걸리는 것은 유상분과 무상분의 구분이다.**

| 출처 | 성격 |
|---|---|
| 퀘스트로 받은 열빙어 | 무상. 매출이 아니다 |
| 구매한 열빙어 | 유상. 이연수익이고 환불 대상이다 |

지금처럼 `capelin_balance` 하나에 섞으면 환불 요청이 왔을 때 얼마가 유상분인지 알 수 없고,
회계상 매출도 가릴 수 없다. 한국 규제도 유상/무상 구분을 기준으로 삼는다.

판매를 붙이는 시점에 필요한 것:

- 잔액을 `capelin_free_balance` · `capelin_paid_balance`로 분리 (마이그레이션 1회)
- **소진 순서 정책** — 무상분을 먼저 쓴다. 유상분이 남아야 환불 여지가 있다
- 결제 지급은 서버가 영수증을 검증한 뒤에만

**지금 미리 나누지는 않는다.** 판매가 확정되지 않았고 나중에 나누는 비용이 크지 않다.
다만 이 항목을 잊고 그냥 팔면 환불 처리에서 막힌다.

**단어 무제한은 차별점으로 내세울 수 있다.** 경쟁 서비스는 자기 서버에 데이터를 두므로
개수 제한이 곧 원가 통제 수단이다. 사용자 Drive에 두면 그 제약 자체가 없다.

## 10. 마이그레이션

### 10-1. 기존 데이터

현재 Hub에 있는 단어를 Drive로 옮겨야 한다. 사용자가 사실상 본인뿐이므로
**일회성 내보내기 스크립트**로 충분하다. 정교한 마이그레이션 UI는 만들지 않는다.

### 10-2. Hub 테이블은 바로 지우지 않는다

코드 경로(push/pull, 단어 REST)만 끊고 테이블은 당분간 남긴다.
문제가 생기면 되돌릴 여지를 두고, 안정되면 `DROP`한다.
**되돌릴 수 없는 삭제를 전환과 같은 날 하지 않는다.**

### 10-3. 구버전 앱

구버전 앱은 여전히 push/pull을 호출한다. 엔드포인트를 즉시 없애면 그 앱들의
동기화가 조용히 실패한다. 최소 한 버전은 엔드포인트를 살려두거나,
**명시적으로 410을 반환하고 앱이 "업데이트가 필요합니다"를 띄우게** 한다.

## 11. 실행 순서 — 그림자 · 검증 · 전환 · 정리

**제약: 전환 기간에도 앱을 매일 쓸 수 있어야 한다.** 한 번에 갈아엎지 않고,
Drive를 먼저 그림자로 돌린 뒤 검증이 끝났을 때만 진실을 옮긴다.

### 11-1. 읽기를 언제 시작하느냐가 유일한 스위치

쓰기는 양쪽에 해도 안전하다. 읽기를 양쪽에서 하면 어느 쪽이 진실인지 모호해진다.
그래서 전환 전까지 **Drive는 쓰기 전용(그림자)** 이다.

| 단계 | Hub | Drive | 진실 | 웹 |
|---|---|---|---|---|
| 1. 그림자 | 읽기·쓰기 | **쓰기만** | Hub | 정상 |
| 2. 검증 | 읽기·쓰기 | 쓰기만 | Hub | 정상 |
| 3. 전환 | 쓰기만 | **읽기·쓰기** | **Drive** | 갈라짐 → 2-3절 결정 |
| 4. 정리 | 차단 | 읽기·쓰기 | Drive | 폐기 또는 읽기 전용 |

3단계는 **플래그 하나로 켜고 끌 수 있게** 만든다(`dart-define` 또는 숨김 설정).
문제가 생기면 즉시 Hub로 돌아올 수 있어야 한다. 이 되돌림 경로가 없으면
전환을 누르는 것 자체가 도박이 된다.

### 11-2. 단계별 작업

| # | 단계 | 작업 |
|---|---|---|
| 1 | 그림자 | Drive 인증(`drive.file`) · 백업 JSON 생성 · appDataFolder 업로드 · **자동 백업 + 실패 노출**(4절) |
| 2 | 검증 | 아래 전환 기준 4개를 실사용으로 통과 · 복원 구현(5절) |
| 3 | 전환 | 읽기 경로를 Drive로 · Hub sync는 쓰기만 유지(되돌림용) · 웹 결정(2-3절) |
| 4 | 정리 | Hub sync 코드 경로 차단 · 구버전 앱에 410 안내(10-3절) · 안정 후 테이블 DROP |

스프레드시트 내보내기·가져오기(6절)와 OCR은 3단계 이후에 얹는다.
**정본이 자리를 잡기 전에 입력 경로를 늘리지 않는다.**

### 11-3. 전환 기준 — 미리 정해두지 않으면 영원히 1단계에 머문다

3단계로 넘어가려면 넷을 전부 통과해야 한다.

1. **자동 백업 연속 성공 30일** — 실사용 중에
2. **복원 실기기 검증** — 앱 삭제 → 재설치 → 복원 → 데이터 일치 확인
3. **실패 노출 동작 확인** — 일부러 네트워크를 끊거나 권한을 회수해서 배너가 뜨는지.
   안 뜨면 결함 A를 그대로 재현하는 것이다
4. **스키마 버전 업 1회 통과** — 책장의 `shelf_id`처럼 필드가 늘었을 때 구버전 백업을 읽을 수 있는지

## 12. 리스크

- **사용자가 Drive 파일을 지운다** — 휴지통에서 30일간 복구 가능하지만 그 뒤엔 없다.
  `appDataFolder`는 Drive UI에 안 보여서 실수로 지울 확률이 낮은 것이 그나마의 방어다
- **Drive API 장애 · 쿼터** — 앱이 로컬 우선이라 당장 쓰는 데는 지장이 없다. 백업만 지연된다
- **계정 전환** — 다른 구글 계정으로 로그인하면 이전 계정의 백업에 접근할 수 없다.
  Firebase 계정과 Drive 계정이 다를 수 있다는 점을 UI에서 명확히 해야 한다
- **OAuth 심사** — `drive.file`은 가볍지만 동의 화면 설정과 앱 검증 절차는 필요하다
- **플랫폼별 설정** — iOS · Android 각각 `google_sign_in` 설정과 키 등록이 필요하다
