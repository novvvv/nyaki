## 1. 게이미피케이션 (streak · 퀘스트 · 츄르)

### 1-1. 퀘스트 목록 (2026-08-27 개정 — 4개로 축소)

| # | 퀘스트 | 조건 | 보상 |
|---|---|---|---|
| 1 | 냐키 쓰다듬기 | 홈 화면 탭 1회 | 5츄르 |
| 2 | 단어 1개 추가하기 | 단어 저장 1회 | 5츄르 |
| 3 | 아침 복습 (TimeQuest) | 06:00–14:00에 `dailyReviewGoal`개 이상 | 1열빙어 |
| 4 | 저녁 복습 (TimeQuest) | 18:00–24:00에 `dailyReviewGoal`개 이상 | 1열빙어 |

하루 상한: 츄르 10 + 열빙어 2.

**"테스트 화면 진입" 퀘스트 제거** — 조건이 진입 1회뿐이라 시간 제약도 없고, 복습을 하려면 어차피
이 화면을 먼저 거친다. 즉 아침/저녁 복습을 깨는 순간 이미 만족하는 **사실상 하위 퀘스트**라
"5개 = 5가지 다른 행동"이라는 취지와 안 맞았다.

1·2는 단발 이벤트(True/False), 3·4는 목표치 카운트가 필요해 **구조가 다르다.**

### 1-2. 서버 권위 방식 (2026-08-20 결정)

기존 단어장 sync(outbox → push → LWW)는 **"누적값"에 안 맞는다** — 오프라인 두 기기가 각자 벌면
나중에 한쪽이 증발한다. 그래서 퀘스트 완료·잔액은 아예 별도 경로로 **서버가 판정**한다.

- `POST /v1/progress/quests/{quest_id}/complete` — idempotent. `QuestStateModel`의 `last_completed_date`가
  오늘이 아니면 서버가 직접 잔액을 올리고 오늘로 UPSERT. 이미 오늘이면 현재 상태만 반환(중복 지급 없음)
- `GET /v1/progress` — 잔액 + 오늘 완료된 questId 목록
- **폴링 타이머 없음** — `GET /v1/progress`는 ① 앱 시작 ② 로그인 직후 ③ 포그라운드 복귀 때만.
  츄르는 대부분 이 세션 안에서 사용자가 직접 트리거하는 이벤트라 폴링이 낭비다

**클라이언트 흐름**: 탭 → 로컬 캐시 낙관적 갱신(즉시 체크) → `POST` → 응답의 잔액으로 캐시 덮어씀
(**서버값이 항상 이김**) → 실패/오프라인이면 재시도 큐(idempotent라 여러 번 보내도 안전)

**스키마** — Hub가 진실: `UserProgressModel`(user_id PK · churu_balance · streak_count · last_active_date ·
daily_review_goal · morning/evening_review_count) · `QuestStateModel`(user_id + quest_id 복합 PK ·
last_completed_date). 로컬 Drift는 **순수 캐시**.

> `QuestStateModel`은 원래 이벤트 로그였는데(2026-08-23 개정) 쓰지도 않는 이력 때문에 row가
> 무한히 쌓이는 게 낭비라 유저×퀘스트당 1 row UPSERT로 단순화했다.

### 1-3. 비로그인 사용자 — 옵션 C: 서버 권위 + 소프트 게이트 (2026-08-22 최종)

서버 권위의 맹점은 **로그인 안 한 사용자가 `POST .../complete`를 아예 못 부른다**는 것.
기능을 막지 않고 **"보상 수령"만 막는다.**

- 퀘스트 목록은 로그인 여부와 무관하게 항상 전부 표시 (궁금증·기대감 유지)
- 각 행에 완료 체크 대신 **자물쇠 아이콘**, 탭하면 "로그인하면 츄르를 모을 수 있어요" 안내
  (화면 전체를 덮는 검은 오버레이는 안 씀)
- 홈 고양이 탭은 항상 동작(순수 로컬 애니메이션), 서버 호출만 로그인 시
- **로컬 전용 이관 로직이 통째로 불필요해진다** — 비로그인 사용자는 애초에 진행을 안 쌓으므로
  "로컬 부트스트랩 → 로그인 시 이관"의 복잡도가 사라진다. 과거 소급은 없음(소프트 게이트가
  계속 로그인을 유도하므로 감수 가능)

### 1-4. 재화 두 종류

**츄르** — 가벼운 참여(탭 1회)의 보상. 하루 상한 10.

**열빙어** (설계만, 미구현) — 원래 퀘스트 5개가 전부 5츄르라 **재화 가치가 행동 난이도와 안 맞았다.**
"냐키 쓰다듬기"(탭 1회)와 "저녁 복습 목표 달성"(실제 학습)이 같은 값이면 복습 보상의 체감이 흐려진다.
진짜 학습 행동에만 나오는 별도 재화로 희소성을 분리한다.

- 소비처는 **수집형·희소 아이템 전용**. 츄르로는 못 사게 막아 "꾸준히 복습해야 얻는 것" 포지셔닝 유지
- **홈에 상시 노출하지 않고 상점/마이페이지에서만** — 평소엔 안 보이다가 상점 갈 때만 보이는 편이 희소성 연출에 맞음
- 신규 출석체크(앱 하루 첫 실행)도 열빙어 지급원 후보 — streak 규칙을 확정할 명분

### 1-5. 소비처 — v1 재선정 (2026-08-28)

**기각한 것과 이유**

- ~~힌트권~~ — **SRS 채점 정직성을 해친다.** 뜻 확인을 유료화하면 모르는데도 "외움"으로 거짓 채점할 유인이 생겨 SM-2 간격이 잘못 늘어난다. 지금처럼 무제한 무료여야 한다
- ~~목표 리셋권 · 복습 스킵권~~ — 무료로 이미 되는 걸(설정 변경, 그냥 넘어가기) 재화로 막는 셈이라 **실제로 해결하는 문제가 없다**
- ~~스트릭 프리즈~~ — 보류. streak 규칙 자체가 미설계라 **지켜줄 streak가 없다**

**채택**

1. **단어장 커버 색상/테마** — 신규 아트 불필요. 순수 코스메틱이라 SRS 무관, 단어장이 쌓였을 때 색으로 구분하는 실용적 가치도 있음
2. **냐키 액세서리** — 기존 고양이 이미지 3장 위에 리본·모자 같은 작은 오버레이 PNG. 스킨 전체를 새로 그리는 것보다 훨씬 저렴
3. (보류) **완주 인증서 프레임** — 진짜 성취에만 연동돼 열빙어 포지셔닝과 잘 맞고 공유 훅으로도 괜찮으나, "완주" 판정 기준(SRS 몇 단계)을 안 정해서 뒤로

**상점 페이지 v1 승격 이유**: 지급만 있고 쓸 곳이 화면에 안 보이면 츄르가 숫자로만 남아 동기부여가 안 된다.

### 1-6. 확률형 아이템 규제 메모 (법률 자문 아님)

츄르·열빙어가 **일일 퀘스트로만 얻어지고 어떤 경로로도 결제로 못 사는 게 확실하면**
국내 확률형 아이템 표시의무(유상 획득 전제) 대상이 아닐 가능성이 높다. 지금은 결제 자체가 없어 리스크 없음.
**결제-재화를 연결하기로 결정하는 시점**(직접 판매든 "구독하면 보너스"든)이 곧 법 검토가 필요해지는 시점.

단, 이와 별개로 **Apple App Store 3.1.1**은 재화의 유·무상과 무관하게 뽑기류 확률 공개를 요구한다 —
뽑기를 켜는 순간 확률 공개 UI가 필요하다.

### 1-7. 미결정

- `dailyReviewGoal` 기본값 · 최소/최대 범위
- **인벤토리 스키마 형태** — 아이템 1종이면 `UserProgress`에 컬럼으로 충분하지만, 스킨 상점을 붙일 걸 고려하면 처음부터 `Inventory`(itemId · count) 테이블이 나을 수 있음. v1 범위만 보면 과설계일 수도
- **오프라인 재시도 큐** — 기존 `SyncOutbox` 재사용(엔티티 타입 추가) vs 별도 큐. `SyncOutbox`는 "payload 통째로" 모델이라 idempotent 커맨드 재시도와 결이 다름
- 퀘스트 목록 확장(서버 정의) — v1은 하드코딩 유지
- 우측 상단 플로팅 아이콘 3개(**우편함 · 상점 · 뽑기**) — v2+ 아이디어. 우편함은 용도부터 미정(보상 수령함 / 공지함 / 선물 기능)

## 2. 책장 (단어장 상위 그룹)

> 설계 완료, 착수 결정 대기.

### 2-1. 확정된 결정

**관계는 1:N, 소속은 필수(NOT NULL).** 단어장은 항상 어떤 책장 안에 있고, "미분류"는 만들지 않는다.
N:M은 조인 테이블이 하나 더 생기고 그것도 동기화 엔티티가 되어야 해서, 지금의
"entity_type + 전체 스냅샷 upsert" 구조에선 삭제 전파·충돌 해소가 눈에 띄게 복잡해진다.

**기본 책장은 고정 id `default-shelf`, 삭제 불가.** 책장을 지우면 안의 단어장은 기본 책장으로 이동한다.
"마지막 책장은 못 지운다" 같은 조건부 규칙보다 **지울 수 없는 착지점 하나를 고정**하는 쪽이
경계 조건이 없어 단순하다. 이름 변경은 가능.

**화면은 3단 계층** — `책장 목록(BookshelfListScreen) → 단어장 목록(BookshelfDetailScreen) → 단어 목록`.
깊이가 2 → 3으로 늘어나므로 완화 장치를 **같은 단계에서 함께** 넣는다:
책장 카드 안에 소속 단어장 이름을 2~3개 칩으로 깔고 **그 칩을 누르면 단어장으로 직행**,
홈 화면에 최근 단어장 바로가기.

### 2-2. 마이그레이션 — 양쪽이 같은 결과에 각자 도달한다

가장 중요한 부분. 순진하게 하면 모든 `word_books`의 `updated_at`이 갱신되며
**앱 업데이트 직후 첫 동기화가 단어장 수만큼의 push로 시작**한다.

**고정 id를 쓰면 앱과 Hub가 서로 통신하지 않고 동일 상태가 된다** → 동기화 트래픽 0건.
(`defaultWordBookId = 'default-nyaki'`에서 이미 쓰고 있는 수법)

- **Hub (alembic)**: `bookshelves` 생성 → 단어장을 가진 유저마다 `('default-shelf', user_id)` 1행 삽입
  (PK가 복합키라 유저별 1행) → `word_books.shelf_id`를 `server_default`로 추가.
  **`updated_at`을 건드리지 않고 `sync_changes`에도 기록하지 않는다.**
- **앱 (Drift v6 → v7)**: `bookshelves` 생성 + 같은 고정 id로 기본 책장 삽입 +
  `shelfId` 컬럼 추가(`withDefault`라 기존 row 자동 백필). **`word_books`를 UPDATE하지 않는다.**

`created_at`이 양쪽에서 달라도 무관하다 — 병합은 `updated_at` 비교이고 기본 책장은 어차피 같은 것을 가리킨다.

### 2-3. 스키마

```dart
@DataClassName('BookshelfRow')
class Bookshelves extends Table {
  TextColumn get id => text()();
  TextColumn get title => text()();
  TextColumn get description => text().nullable()();
  IntColumn get sortOrder => integer().withDefault(const Constant(0))();
  DateTimeColumn get createdAt => dateTime()();
  DateTimeColumn get updatedAt => dateTime()();
  BoolColumn get isDeleted => boolean().withDefault(const Constant(false))();
  @override Set<Column<Object>> get primaryKey => {id};
}
// WordBooks에 추가 — references()를 걸지 않는다 (ARCHITECTURE.md §4.3)
TextColumn get shelfId => text().withDefault(const Constant('default-shelf'))();
```

**`sortOrder`를 처음부터 넣는 이유**: 사용자가 직접 만드는 분류라 "위로 올리기" 요구가 반드시 온다.
나중에 넣으면 앱 스키마 + Hub 마이그레이션 + 동기화 스냅샷을 한 번 더 손봐야 한다. 지금은 컬럼 하나다.

### 2-4. 동기화

- `entity_type`에 `'bookshelf'` 추가 — `SyncMutation`의 `Literal`, outbox, `_mergeBookshelf`,
  `_push`의 payload 키 매핑(3분기), `bootstrapLocalEntitiesForSync`
- `_apply_mutation`에 **bookshelf 분기를 맨 앞에** — 지금은 "word_book이 아니면 전부 word"라 안 넣으면 책장이 단어로 처리된다
- **서버가 pull 배치의 참조를 보강**해야 한다 (ARCHITECTURE.md §4.3) — 단어장 이동은
  "이미 있는 자식을 나중에 만든 부모로 옮기는" 동작이라 페이지 경계에서 고아가 생긴다.
  필수 소속 + 3단 계층에서는 고아 단어장이 **어느 목록에도 안 나타나 접근 경로가 사라진다**
- 조립 단계에 fallback(못 찾은 책장 → 기본 책장에 얹어 표시). **DB는 고치지 않는다** — 고치면
  `updated_at`이 갱신돼 올바른 값이 병합 가드에 막히고, 잘못된 값이 전 기기로 퍼진다
- **배포는 Hub 먼저** — 구버전 서버는 `bookshelf` mutation을 422로 거절한다

### 2-5. API

| Method | Path | 비고 |
|---|---|---|
| GET | `/v1/bookshelves` | `sort_order`, `created_at` 순 |
| PUT | `/v1/bookshelves/{id}` | upsert |
| DELETE | `/v1/bookshelves/{id}` | soft delete + 소속 단어장을 `default-shelf`로 이동. **`id == 'default-shelf'`면 409** |

DELETE는 두 테이블을 건드리므로 `sync_changes`에 **책장 1건 + 이동된 단어장 N건**을 모두 기록해야 한다.
빠뜨리면 다른 기기에 유령 책장 + 고아 단어장이 생긴다. (같은 실수가 `delete_word_book`에 이미 있다 — TASKS.md §2-3)

### 2-6. 실행 순서 (7단계)

| # | 범위 | 비고 |
|---|---|---|
| 1 | Hub 스키마 + alembic 백필 | 앱보다 먼저 배포 |
| 2 | Hub API + 동기화 + 배치 참조 보강 + `hasMore` + `exclude_unset` | 1과 같은 배포 |
| 3 | 앱 Drift v7 + `Bookshelf` 모델 + 저장소 + fallback 조립 | **UI 없음, 화면 변화 0** |
| 4 | 앱 동기화 (outbox·merge·bootstrap·적용 순서·실패 노출) | 3과 묶음 |
| 5 | 앱 UI (책장 목록·상세·이동 시트·탭 교체) | 사용자에게 처음 보임 |
| 6 | 범위 지정 — **책장 단위 테스트**, 홈 due 표시 | 아래 |
| 7 | 문서 갱신 | |

**6단계가 책장의 진짜 효용이다.** 분류 자체보다 **범위 지정** — "영어 책장만 복습".
이게 없으면 책장은 탭을 한 번 더 하게 만드는 폴더일 뿐이다.

### 2-7. 미결정

- 기본 책장 이름 — `기본 책장` / `내 책장` (사용자가 바꿀 수 있으니 초기값만)
- 이모지 컬럼 — Design.md가 4색 고정이라 색 구분은 팔레트 원칙과 충돌. 이모지 한 글자가 안전한 절충
- 중첩 책장 — **하지 않기를 권한다.** `parentId`를 넣는 순간 순환 참조 검증·깊이 제한·이동 UI가 따라온다
- 책장 단위 암기율 — 단어장 암기율의 단순 평균은 단어 수를 무시하므로 **단어 단위 가중 평균**이어야 함
- 책장이 하나뿐일 때 목록 화면을 건너뛸지 — 권하지 않음. 두 번째를 만드는 순간 화면이 바뀌어 길을 잃는다

**이번에 안 하는 것**: N:M · 중첩 · 공유/공개 · 책장 단위 CSV 내보내기(CSV 기능 자체가 미구현)

## 3. 단어 사진 첨부

### 3-1. 현재 상태 — 배관은 뚫려 있고 UI·저장소만 없다

`image_path`는 이미 전 계층에 있다: `Word` 모델 · Drift 컬럼 · `Create/UpdateWordInput` ·
repository 2종 · `sync_coordinator` 직렬화 · Hub `WordModel.image_path` · 웹 타입 정의 ·
테스트 세션의 `_WordImage`(`assets/` 접두사 분기).

**없는 것**: 사진 선택 UI 전부 · `image_picker` 의존성 · iOS/Android 권한 · 업로드 엔드포인트 ·
웹 업로드 UI(`api-client.ts`가 `image_path: null` 하드코딩) · 목록/상세 썸네일.
지금 앱에 보이는 사진은 시드 데이터 한 장뿐.

### 3-2. 결정 — 자체 Hub 저장 (Firebase Storage 기각)

1. **데이터 일원화** — 단어는 이미 자체 Postgres. 사진만 Firebase면 백업·계정삭제·이전 시나리오가 두 벌이 된다. **Firebase는 "인증만" 담당하는 선을 유지**
2. **계정 삭제**(P0) — Postgres row 지우면서 파일도 같이 정리하면 끝
3. **개인정보처리방침** — "자사 서버 저장" 한 줄. 국외 이전 고지 불필요
4. **비용 예측 가능** — Lightsail 플랜에 포함, 추가 0원. Firebase Blaze는 무료 한도가 커도 **지출 상한이 없다**(버그·트래픽 급증 시 청구서 무한)

포기하는 것: CDN · 자동 리사이징 · 업로드 재시도 인프라(직접 구현하거나 없이 감).
재검토 조건: 디스크·대역폭이 부담되면 S3 이전 — `image_path`가 URL 문자열이라 이전 비용이 낮다.

### 3-3. 스키마 — 한 컬럼 3의미 문제를 분리

| 컬럼 | 동기화 | 용도 |
|---|:---:|---|
| `image_path` | O | 원격 URL(또는 시드 에셋 경로). **정본** |
| `image_local_path` | — | 촬영 원본 / 다운로드 캐시 |
| `image_upload_pending` | — | 업로드 대기 플래그 |

**표시 규칙(앱·웹 공통)**: ① `image_local_path` 있으면 `Image.file` → ② `assets/`로 시작하면 `Image.asset`
→ ③ 그 외 `Image.network`. Drift `addColumn` 2개(기존 row는 null이라 무영향), Hub·웹은 마이그레이션 없음.

### 3-4. 업로드 흐름

```
선택 → 압축(1024px, quality 85 → 200KB 내외) → 앱 디렉터리 복사 + pending=true
     → 즉시 화면 표시 [여기까지 오프라인 동작]
     → 네트워크 되면 POST /v1/media → 응답 URL을 image_path에 기록, pending 해제
     → outbox upsert → 기존 sync 경로로 Hub 반영 → 웹·타기기는 URL로 조회
```

**핵심**: 업로드는 `sync_coordinator`와 **별도 경로**다. sync에는 URL 문자열만 흐르므로 기존 outbox 구조 무변경.
압축은 필수 — 요즘 폰 사진이 3~5MB라 안 하면 업로드 시간·대역폭이 터진다.

### 3-5. 보안 요구사항

Caddy 정적 서빙에는 인증이 없으므로 **현실적 위협은 URL 추측**이다.

1. **파일명 랜덤 UUID** — 단어 ID·순번 금지. 122비트 난수(capability URL 모델)
2. **업로드 검증** — magic byte로 실제 이미지 확인(확장자 불신), 용량 상한 5MB, 사용자 파일명 그대로 안 씀(path traversal)
3. **소유권 확인** — 대상 단어가 요청자 uid 소유인지 (`get_current_user_id` 재사용)
4. **응답 헤더** — Content-Type 화이트리스트 + `X-Content-Type-Options: nosniff`
5. **디렉터리 브라우징 off**
6. **서버 재인코딩** — Pillow 디코딩 후 재저장. 폴리글랏 파일 무력화 + **EXIF 제거로 GPS 유출 방지**

> 참고: Firebase도 안전한 게 아니다 — Storage Rules `allow read: if true`가 업계 최다 유출 사고 원인이다.
> 양쪽 다 **설정 실수가 유일한 현실적 위험.**

### 3-6. 비용 · 단계

Lightsail $5 플랜(40GB SSD · 월 2TB 전송, 이미 지불 중) / 예상 200KB × 단어 1만 개 ≈ 2GB / **추가 0원**

| 단계 | 내용 | 견적 |
|---|---|---|
| 1 | **앱 로컬 사진** — `image_picker`, **iOS `Info.plist` 권한 문구**(현재 usage description이 하나도 없음 = App Store 단골 반려), Drift 마이그레이션, 압축·복사 유틸, 공용 폼 위젯, 썸네일 | 반나절 |
| 2 | **서버 업로드** — `python-multipart`·`Pillow` 추가(**현재 둘 다 없음**), `POST /v1/media`, 삭제 시 파일 정리, Caddy `/media` 라우트, 볼륨, 테스트. Alembic 불필요 | 1일 |
| 3 | **앱 업로드 큐** — pending 스캔 → 업로드 → 갱신 → outbox, 재시도·오프라인 대기. **가장 버그 나기 쉬운 구간** | 1일 |
| 4 | **웹** — 업로드 UI, 하드코딩 제거 | 반나절 |
| 5 | 디스크 모니터링·백업, QA | 반나절 |

**합계 4~6일 풀타임 / 2주 안팎 파트타임.** 1단계만으로 서버 없이 배포 가능한 상태가 된다.

### 3-7. 선결 과제 — `UpdateWordInput`의 null 의미

현재 `imagePath == null`이 **"변경 없음"**으로 해석되어 **사진 삭제를 표현할 수 없다.**
삭제 기능을 1단계에서 빼면 회피 가능하고, 넣으려면 sentinel 값 또는 `Value<String?>` 래퍼 전환
(repository 2개 + 호출부 전체 수정). `pronunciation`·`description`·`example`도 같은 문제라 언젠가 고쳐야 한다.

**미결정**: 삭제 기능을 1단계에 넣을지 / 사용자당 사진 개수·용량 쿼터(Pro 차별화 요소 가능) /
단어당 1장 고정 vs 복수(현재 스키마는 1장 전제)

**리스크**: `build_runner` 재생성 실패(툴체인 먼저 확인) / iOS 권한 문구 미기재 반려 /
업로드 큐 무한 재시도(상한·백오프) / 디스크 포화 / 고아 파일 누적

## 4. J-POP 유입 전략 (별도 프로젝트)

### 4-1. 왜 이 방향인가

목표는 **포트폴리오 겸 수익화(수익은 나면 좋은 정도)**.

범용 영단어 앱은 레드오션이다 — Anki가 SM-2 무료, 퀴즐렛·클래스카드 무료 티어.
Pro가 파는 게 "동기화와 쿼터"면 월 4,900원의 근거가 약하다. **사용자는 인프라에 돈을 내지 않는다.**

반면 "J팝/애니로 일본어 배우는 사람"은 명확한 니치다. 가사 → 단어 추출 → 학습 흐름은 범용 단어장 앱이
못 따라오고, **유입(콘텐츠) → 학습(앱) → 리텐션(SRS)**이 한 줄로 이어진다.

**유입 산수**: 무료 앱 유료 전환은 통상 1~3%. 월 10만원이면 유료 20명 → 활성 1,000명 안팎 →
블로그·유튜브 트래픽 **수만 단위**가 필요하다. 수익을 주목적으로 잡으면 수지가 안 맞는다.

### 4-2. 구조 — 채널 분리로 리스크 격리

```
유튜브 (가사+번역 영상 · 수익창출 OFF)
   │ 링크
   ↓
블로그 (100% 자체 저작물: 단어·문법·해설·아티스트 정보)
   │ 담기 버튼
   ↓
냐키 앱 (단어장 · SM-2 복습)
```

**핵심 원칙: 자체 도메인·애드센스·앱이 붙은 쪽에는 남의 저작물을 두지 않는다.**

- **유튜브**: 가사·번역 영상은 여기에만. 해당 영상 수익창출 OFF. 음원은 Content ID가 잡아 권리자에게 수익이 가므로 내릴 유인이 적다
- **블로그**: 곡 메타데이터(아티스트·발매일·앨범·노래방 번호·차트 순위 = **사실 데이터라 저작권 대상 아님**) /
  곡의 단어 N개 + 뜻 / 핵심 표현 3~5개 해설 / 원문 가사·MV는 **외부 링크만**

### 4-3. 저작권 판단 근거

**왜 가사 전문을 자체 호스팅하지 않는가** — 집행은 소송이 아니라 **플랫폼 차단**으로 온다.
JASRAC·한음저협은 개인 고소 대신 호스팅·애드센스·앱스토어에 신고하고, 예고 없이 사이트가 내려가거나
애드센스가 정지되면서 **자체 제작 부분까지 같이 죽는다.**
"나무위키·티스토리도 하는데?"는 합법이라서가 아니라 아직 문제 삼지 않은 것이다 —
위키는 게시자가 불특정 다수라 책임이 흩어지고, 국내 포털 블로그는 플랫폼 라이선스 우산이 있을 수 있다(**미확인**).
자체 도메인 + 애드센스 + 앱 연동이면 "개인 블로그"가 아니라 **책임 주체가 명확한 사업자**로 보인다.

**저작권이 보호하는 건 표현이지 사실·정보가 아니다.**

| 안전 | 위험 |
|---|---|
| 곡에 나온 단어·문법·관용구(언어의 공용 재산) | 가사 전문 게재 |
| 곡 메타데이터(아티스트·발매일·노래방 번호) | 전곡 줄별 번역 |
| 한두 구절 인용 + 긴 해설 | 형식만 바꿔 전문 재구성이 가능한 자료 |
| 원문 순서와 무관하게 재구성한 단어장 | |

판단 기준은 **"얼마나 가져왔나 / 원본을 대체할 수 있나"** — 자료 전체로 원곡 가사를 복원할 수 있으면 이름표만 바꾼 셈이다.

**유튜브 리스크** — 두 겹 권리(음원은 Content ID 자동 정산 / **번역 가사는 별개 권리라 Content ID가 안 잡고 묵인**).
수익창출 OFF는 합법화가 아니라 "권리자가 움직일 유인을 줄이는" 효과.
실질 제재는 채널 단위: Content ID 클레임(무해) → 지역 차단 → 저작권 경고, **3회면 채널 삭제**.
경고는 대개 하나씩 오고 **90일 후 만료**되므로 첫 경고 시 해당 레이블 곡을 빼는 식으로 대응할 시간이 있다.
수익화된 블로그로 트래픽을 보내면 "비영리" 방어가 약해지므로 **"수익 안 내니 괜찮다"를 근거로 삼지 말 것.**

**기각: 채널 다중화** — ① 구글은 계정 단위로도 보고 반복 패턴을 "정책 우회"로 판단해 연결 채널까지 정지 가능
② 삭제된 채널 운영자의 새 채널 개설 자체가 약관 위반 ③ 구독자·알고리즘 신뢰도가 쪼개져 성장 1/N.
대신 (a) 민감한 권리자/레이블 파악해 회피 (b) **유튜브 밖 독립 유입 경로 확보**.

**단일 실패점**: 유튜브가 유일 유입구면 막히는 날 트래픽 0 → 검색으로 독립 유입되는 블로그 콘텐츠를 병행 축적.

### 4-4. 기술 스택

- **별도 Next.js 프로젝트** (nyaki 폴더 밖, 새 레포) + **별도 도메인** — 브랜드·SEO 주제 일관성 + 리스크 격리
- **백엔드는 새 서버 불필요** — 같은 Lightsail에서 Postgres 스키마/DB만 분리, FastAPI 프로세스 별도 기동.
  곡 데이터는 자주 안 바뀌므로 Next.js가 빌드/ISR 시점에 DB를 직접 읽는 방식도 가능
- **로그인은 nyaki와 같은 Firebase 프로젝트** → UID가 같아 계정 연결 없이 "가사 → 냐키 단어장 저장" 연동 가능.
  Firebase 콘솔의 **Authorized domains에 새 도메인 추가** + 동일 config 복사.
  가사/학습 페이지는 완전 공개(크롤러 접근 보장), 로그인은 단어 저장 시에만
- URL: `/artist/[slug]`, `/artist/[slug]/[song-slug]` / 모델 초안: `Artist` · `Song`(제목 원어·로마자·한글, 발매일, 노래방 번호) · `ChartSnapshot` · `TourEvent`

**왜 nyaki web에 안 붙이는가**: nyaki web은 로그인·설정 위주의 작은 앱이고 가사 사이트는 수천 페이지 콘텐츠 사이트다.
빌드 시간·배포 주기·ISR 전략이 완전히 다르고, 한 도메인에 "단어 암기 앱"과 "J팝 가사"가 섞이면 SEO 주제 일관성도 떨어진다.

## 5. 복습 캘린더 · 도장 (아이디어)

날짜별 복습 활동을 달력(잔디밭/히트맵)으로. `srsLastReviewedAt` 기준 **로컬 집계만으로 가능**해 보인다.

**정할 것**: 어디에 넣을지(단어장 정보 탭 / 마이페이지 / 별도 화면) · streak와 시각적으로 묶을지
(streak가 생기면 "연속 학습일"을 달력 위에 하이라이트하는 조합이 자연스러워, 둘을 같이 설계하는 게 나을 수도)

**상점과 결합 — "캘린더 도장(스탬프)"**: 요즘 "다꾸"(다이어리 꾸미기) 감성으로, 재화로 산 도장 디자인
(하트·발바닥·계절 테마)을 그날 캘린더에 찍는 방식. **캘린더와 상점 백로그 둘을 하나로 묶는 아이디어**라
효율적이고, SRS 정직성과 무관한 순수 코스메틱이라 안전하다 — **1순위 상점 아이템 후보.**

**도장 도감(컬렉션 앨범)**: 모은 도장을 모아보는 화면. 보유는 컬러, 미보유는 실루엣으로 보여주고
"24/40개 수집" 진행률 표시. 두 재화와도 자연스럽게 연결된다 —
일반 도장은 츄르로 상시 구매, **희귀/시즌 도장(크리스마스·벚꽃)은 열빙어 전용**.

→ 캘린더 하나로 "매일 쓰는 재미(도장 찍기) + 모으는 재미(도감) + 두 재화를 다르게 쓰게 하는 것"이 다 엮인다.

**우선순위 낮은 다른 다꾸류**: 단어 카드/스티커(어디에 "고정"할지 애매해 설계 부담이 큼) ·
단어장 표지 꾸미기 확장(색상만 먼저 가고 나중에 패턴·스티커로 넓히는 편이 나음)
