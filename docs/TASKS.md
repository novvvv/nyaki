## 0. 지금 당장 (2026-09-01 기준)

```
1. flutter analyze / test 돌려서 리디자인 브랜치 닫기
2. 동기화 실패 노출 + Crashlytics  ← 같은 작업. 출시 전 필수
3. Drift 마이그레이션 실기기 검증   ← 미루면 검증 대상이 누적됨
4. 그 다음에 책장이든 기능이든
```

**2번을 묶는 이유**: Crashlytics는 크래시를, 동기화 실패 배너는 조용히 멈춘 sync를 드러낸다.
목적이 같다 — "문제가 생겼을 때 알 수 있게 하기". 지금은 둘 다 없어서
출시 후 사용자가 "안 돼요"라고 하면 알 방법이 없다.

**3번을 미루면 안 되는 이유**: 책장이 Drift v7을 얹을 예정이라, v6까지 지금 검증해두면
v7은 그 위에 하나만 확인하면 된다. 건너뛰면 나중에 v4~v7을 한꺼번에 봐야 한다.

## 2. Hub · 동기화 기술부채

> 원인 분석과 수정 상세는 [ARCHITECTURE.md §4](ARCHITECTURE.md#4-동기화).

### 2-1. 동기화 실패가 무증상이다 (결함 A) — 가장 급함

`_push`가 outbox 100건을 한 묶음으로 보내는데 **하나라도 서버가 거절하면 배치 전체가 실패**한다.
서버에만 있는 길이 제한(`term` 500자 등)에 걸리는 값이 하나 들어가면 그 기기의 모든 변경이
**영원히** 서버에 못 간다. 그런데 `catch (_) {}`라 화면에도 로그에도 표시가 없다.

- [ ] 1단계 — 예외 로깅 + 연속 실패 카운터 (작음)
- [ ] 2단계 — 임계치 초과 시 설정 화면에 배너 (작음, **이것만으로 무증상이 사라짐**)
- [ ] 3단계 — 4xx면 배치를 반으로 쪼개 문제 1건을 dead letter로 격리
      → **CSV 가져오기를 만들기 전까지.** 외부 파일이 들어오면 확률이 급등한다

### 2-2. FK(외래키) — 넣지 않기로 결론 (2026-09-01)

- [x] ~~FK 제약 추가~~ — 2026-08-22엔 "`ForeignKey()` 추가 + 마이그레이션이면 해결"로 적혀 있었으나 두 가지가 틀렸다.
      ① 앱 Drift에는 **선언이 이미 있다**(`WordEntries.wordBookId`). 다만 `PRAGMA foreign_keys = ON`이
      없어 강제되지 않을 뿐. ② **추가하면 위험하다** — pull 트랜잭션이 롤백되면 cursor도 롤백되어
      동기화가 무증상으로 영구 정지한다.
      → 대신 서버가 pull 배치의 참조를 보강하고, Drift 선언 옆에 "의도적으로 강제하지 않음" 주석을 남긴다

### 2-3. 나머지 결함

- [ ] **삭제가 절반만 전파 (B)** — 서버는 단어장 삭제 시 단어도 지우면서 `sync_changes`엔 단어장만 기록. 앱은 단어를 아예 안 지움 → 지운 기기·서버·다른 기기가 서로 다른 상태 → **책장 작업과 함께**
- [ ] **`sync_changes` 무한 증가 (C)** — 1년 쓰면 새 기기 첫 동기화가 12분(무표시). 단기는 `hasMore` 루프, 중기는 스냅샷 응답 → **사용자 늘기 전에**
- [ ] **부모 미확인 (D)** — REST 경로는 확인하는데 동기화 경로는 안 함. 안 터지는 이유가 앱 코드에만 있음
- [ ] **시계 신뢰 (E)** — 병합이 기기가 보낸 `updated_at`을 그대로 믿음. 서버 시각 상한 보정으로 완화
- [ ] **N+1 (F)** — pull이 로그 줄마다 조회. C를 고치면 같이 사라짐
- [ ] **cursor 정체 (G)** — 현재 발생 불가(soft delete만), 수정은 한 줄이라 손대는 김에
- [ ] **`model_dump(exclude_unset=True)`** — 구버전 클라이언트가 모르는 필드를 지우는 문제. 한 줄

## 6. 단어장 정보 탭 · 통계

- [ ] **정보 탭 — 일부 구현** (2026-09-01 갱신)

  **(2026-09-01) 점수 모델 교체** — 기존 `srsIntervalDays / 30 × 100`(선형)은 SM-2 간격이
  1 → 3 → 8 → 20 → 50일로 지수적으로 늘어나는 걸 선형으로 나눠서 **첫 성공이 3점**에 그쳤다
  (단어 2개를 한 번씩 외운 단어장이 2점으로 표시됨).
  `log(1 + 간격) / log(1 + 30) × 100`으로 교체 → 같은 단계가 **20 / 40 / 64 / 89 / 100**.
  지표 이름도 '평균 암기 점수' → **'단어장 암기율'**(분모는 단어 전체).
  캡션·격자선·축 라벨·평균 점선 제거, 꺾은선 → Catmull-Rom 곡선 + 그라데이션 면.

  **아직 안 된 것** — 아래 6개 중 이거 하나만 됨:
  1. 총 단어 수 · 오늘 복습 개수
  2. **학습 단계 분포 4단계** — 신규(`repetitions == 0`) / 학습 중(`repetitions` 1~2 & `intervalDays < 7`) / 복습 중(`intervalDays` 7~30) / 장기 기억(`intervalDays >= 30`)
  3. 즐겨찾기 개수
  4. 마지막 학습일 (`srsLastReviewedAt` 최댓값)
  5. 생성일
  6. 밀린 복습 개수 (`srsDueAt`이 7일 이상 지난 단어, 0이면 숨김)

  P2 후보(당장은 과함): 평균 ease factor · 자주 틀리는 단어 Top3(`srsLapses` 내림차순) · 주간/월간 추가 추이

  **스키마 변경 불필요** — SM-2 필드가 이미 전부 있어서 로컬 집계만으로 된다.

- [ ] **`gradeAgain`의 점수 리셋** (미해결) — '모름'을 누르면 `intervalDays`가 0이 되어
      50일까지 올린 단어가 100점 → 0점이 된다. 실제로 다 잊은 건 아니므로 `lapses`나

로그인 UI/Hub 코드는 두고 **본인 테스트 계정만 실제 클라우드 sync**, 나머지는 로컬 전용처럼 동작시키는 선택지.
서버에서 막아야 실효성 있다(클라이언트 판단은 우회 가능) — `get_current_user_id`에 이메일 allowlist 체크
`require_sync_access` 의존성을 추가해 `/v1/sync/*`에만 적용. `.env`에 `SYNC_ALLOWED_EMAILS=...` 추가로 끝,
**DB 마이그레이션 불필요**. 나중에 요금제 붙일 때 `role` 컬럼으로 확장 가능.

**부작용**: 403을 받으면 `catch (_) {}`가 삼키고 재시도를 반복해 **outbox가 무한 적재**된다
(§2-1과 같은 문제). 403 시 타이머 중단 로직이 먼저 필요하다.

## 9. 실행 리듬 — 앱 vs 콘텐츠

**결론: 병렬, 단 비중은 앱에.** "앱 완성 후 콘텐츠 시작"은 안 한다 — 시간의 성질이 다르다.

| | 성질 | 소요 |
|---|---|---|
| 앱 P0 | 유한한 작업, 끝이 정해짐 | 집중하면 1~2주 |
| 콘텐츠 | 리드타임 김(색인·순위 대기) | 3~6개월 |

- 앱을 다 만든 뒤 콘텐츠를 시작하면 출시 시점 유입 0 → 또 몇 달 대기
- **1~2주차**: 평일 대부분을 P0에. 콘텐츠는 **주 2~3개, 한 편 30분 안쪽** — 완성도보다 개수·꾸준함
- **첫 콘텐츠는 저작권 무관한 것부터** — 노래방 번호·차트 순위·아티스트 정보. 사실 데이터라 리스크 0인데 검색 수요 있음
- **P0 끝나면 유입 없어도 바로 출시** — 심사에 1~2주 + **첫 심사 리젝 확률 높음**. 사용자 없는 지금이 마음 편히 버그 고칠 시기
- **3주차부터 콘텐츠 주력 전환** — 앱은 P1을 천천히, 블로그는 주 3~4개로
- **번아웃 방지**: "매일" 대신 **"주 N개"**, 못 지킨 주는 그냥 넘어가는 구조
