> 2026-08-06 작성. 출시(스토어 배포) 전에 반드시 끝내야 할 것과 미뤄도 되는 것을 우선순위로 정리. 기능 ID는 [features-v0.1.md](notes/product/features-v0.1.md) 기준.
> 관련 문서: [next-v0.1.md](notes/product/next-v0.1.md) · [pricing-v0.2.md](notes/product/pricing-v0.2.md) · [docs/SRS.md](docs/SRS.md)

## 결론 먼저 — 가장 시급한 3가지

1. **HTTPS·도메인 (F-S-03)** — 지금 Hub가 `http://43.203.79.229` 평문이다. 로그인 토큰과 사용자 데이터가 암호화 없이 오간다. iOS는 ATS(App Transport Security) 때문에 평문 HTTP를 쓰면 **App Store 심사에서 막히거나 예외 설정을 요구받는다.** 출시 전 반드시 해결.
2. **데이터 유실 방지 검증 (SM-2 + sync)** — 방금 SM-2를 넣으면서 Drift 스키마를 v4로 올렸다. 기존 사용자 데이터가 마이그레이션에서 깨지면 복구 방법이 없다. 실기기 업그레이드 시나리오 테스트 필수.
3. **모니터링·크래시 리포팅** — 출시 후에는 사용자가 "안 돼요"라고만 말한다. 크래시 로그가 없으면 원인 파악이 불가능. Firebase Crashlytics 정도는 출시 전에 붙여야 한다.

나머지(게이미피케이션, 요금제 과금, Drive 백업, 전면 UI 리뉴얼)는 **출시 후에 해도 되는 일**이다. 이유는 아래 각 섹션에.

## P0 — 출시 전 필수 (이거 없으면 출시 불가)

### 1. HTTPS · 도메인 (F-S-03)

- [ ] 도메인 구매 후 Lightsail IP 연결
- [ ] Caddy에 자동 TLS 설정 (Let's Encrypt)
- [ ] `api/.env`의 `CORS_ORIGINS` 실제 도메인으로 교체 (현재 `your-domain.example` 플레이스홀더)
- [ ] 앱 `NYAKI_API_BASE_URL` · 웹 `NEXT_PUBLIC_API_BASE_URL`을 https로 교체
- [ ] iOS ATS 예외 설정이 남아있다면 제거

**왜 P0인가**: 평문 HTTP로 Firebase ID 토큰이 오간다. 보안 문제이자 심사 리스크.

### 2. 데이터 마이그레이션 · 유실 검증

- [ ] Drift schemaVersion 3 → 4 업그레이드 시나리오 실기기 테스트 (기존 데이터가 있는 상태에서 새 빌드 설치)
- [ ] 마이그레이션 실패 시 앱이 죽지 않고 복구되는지 확인
- [ ] SM-2 필드가 sync push/pull에서 정상 왕복하는지 (앱→Hub→다른 기기)
- [ ] 오프라인에서 채점 → 온라인 복귀 시 outbox가 밀리는지

**왜 P0인가**: 데이터가 날아가면 사용자가 돌아오지 않는다. 코드 버그는 고치면 되지만 유실은 되돌릴 수 없다.

### 3. 크래시 리포팅 · 최소 로깅

- [ ] Firebase Crashlytics 연동 (Firebase 이미 쓰고 있어서 추가 비용 없음)
- [ ] Hub(FastAPI) 서버 에러 로그 파일 저장 + 로테이션
- [ ] 로그에 개인정보(이메일·토큰·단어 내용) 안 남기는지 확인

**왜 P0인가**: 출시 후 문제 발생 시 원인 파악의 유일한 수단.

### 4. 기본 QA (F-QA-01)

- [ ] `flutter analyze` · `flutter test` 전체 통과 (아직 미완료)
- [ ] 핵심 플로우 수동 테스트: 가입 → 단어장 생성 → 단어 추가 → 테스트 → 채점 → sync → 재로그인 후 데이터 확인
- [ ] 신규 설치 첫 실행 (빈 상태) 에러 없는지
- [ ] 네트워크 끊긴 상태에서 앱 전체 동작

### 5. 스토어 제출 준비물

- [ ] 개인정보처리방침 페이지 (Firebase 로그인·데이터 수집 항목 명시) — **App Store 필수**
- [ ] 앱 아이콘·스크린샷·설명문
- [ ] 계정 삭제 기능 — Apple이 로그인 있는 앱에 **의무화**한 항목. 현재 없으면 리젝 사유
- [ ] 연령 등급·데이터 수집 신고 (App Privacy)

## 실행 리듬 — 앱 개발 vs 콘텐츠, 어느 쪽 먼저?

### 결론: 병렬. 단 비중은 앱에 둔다

**"앱을 완성하고 나서 콘텐츠 시작"은 하지 않는다.** 두 작업의 시간 성질이 다르기 때문이다.

| | 성질 | 소요 |
|---|------|------|
| 앱 P0 | 유한한 작업 — 끝이 정해져 있음 | 집중하면 1~2주 |
| 콘텐츠 | 리드타임이 김 — 색인·순위까지 대기 | 3~6개월 |

앱을 다 만든 뒤 콘텐츠를 시작하면 출시 시점 유입이 0이라 아무도 안 받는 앱이 되고, 거기서 또 몇 달을 기다려야 한다. 지금 콘텐츠를 시작해두면 P0를 끝낼 때쯤 첫 유입이 잡히기 시작한다.

다만 콘텐츠를 매일 만들면서 개발까지 하면 둘 다 흐지부지된다 → **초기 2주는 개발 주력, 콘텐츠는 최소한만.**

### 1~2주차 — 개발 주력

- 평일 시간 대부분을 위 P0 체크리스트에 (순서는 추천 진행 순서 표 그대로)
- 도메인은 가사 사이트에도 필요하니 이번에 같이 구매
- 콘텐츠는 **주 2~3개, 한 편 30분 안쪽**으로만. 완성도보다 개수·꾸준함

### 첫 콘텐츠는 저작권 무관한 것부터

노래방 번호 정리 · 월간/연간 차트 순위 · 아티스트 기본 정보 — 전부 **사실 데이터라 리스크 0**인데 검색 수요는 실제로 있다("○○ 노래방 번호" 등). 이걸로 도메인 신뢰도를 먼저 쌓으면 나중에 학습 콘텐츠를 올릴 때 색인 속도가 빨라진다.

**유튜브(가사·번역 영상)는 뒤로 미룬다** — 편집 비용이 커서 지금 시작하면 개발이 멈춘다. 블로그가 먼저. (구조는 [JPOP-FUNNEL-PLAN.md](JPOP-FUNNEL-PLAN.md) 참고)

### P0 끝나면 바로 출시

유입이 없어도 미루지 않는다:

- 심사에 1~2주 걸리고 **첫 심사는 리젝될 확률이 높다** → 왕복 시간을 미리 벌어둔다
- 초기엔 사용자가 없으니 지금이 마음 편히 버그 고칠 수 있는 시기

### 3주차부터 — 콘텐츠 주력으로 전환

- 앱: P1(단어장 수정·삭제, 테스트 결과 요약)을 천천히
- 블로그: 주 3~4개로 늘리고 학습 콘텐츠(곡별 단어·문법) 섞기 시작

### 번아웃 방지

혼자서 개발·콘텐츠·마케팅을 다 하면 3개월 안에 지치는 게 보통이다.

- "매일"이 아니라 **"주 N개"**로 잡는다
- 못 지킨 주가 있어도 그냥 넘어가는 구조로 만든다
- 목표가 포트폴리오 + 수익(나면 좋은 정도)이므로, 수익 압박으로 페이스를 올릴 이유가 없다
