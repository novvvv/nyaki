# 웹 복습 기능 (설계안)

> 웹에서도 테스트(복습)를 할 수 있게 하는 설계안. 채점 결과를 **어떻게 서버에 보낼지**가 핵심이다.
> 2026-09-15 작성. 착수 확정 시 [PLANS.md](PLANS.md)로 통합하고 이 파일은 지운다.
> 현재 구조는 [ARCHITECTURE.md](ARCHITECTURE.md), 진행 상태는 [TASKS.md](TASKS.md).

---

## 1. 결론

**채점 결과를 메모리에 쌓았다가 세션이 끝날 때 한 번에 보낸다.**

테스트 세션 한 번에 HTTP 요청은 **2번**이다.

```
세션 시작   →  GET  /v1/review/due?limit=30    출제할 단어 받기
카드 30장 채점  →  (요청 없음, 메모리에 누적)
세션 종료   →  POST /v1/review/grades          30장 결과를 한 번에
```

카드마다 보내는 방식과 비교하면 이렇다.

| | 요청 수 | 전송량 |
|---|---|---|
| 카드마다 `PUT /words/{id}` | 30 | 약 15KB — 단어 전체를 30번 재전송 |
| 세션 끝에 `POST /review/grades` | 1 | 약 2KB — id·등급·시각만 |

지금 웹이 단어를 고칠 때마다 `PUT`으로 **20개 필드짜리 단어를 통째로** 보낸다.
`"이거 맞혔어요"` 한마디에 이 페이로드를 쓰는 건 낭비다.

## 2. 근거

조사한 실제 서비스들의 방식. 2026-09-15 확인.

| 서비스 | 방식 | 출처 |
|---|---|---|
| **Duolingo** | **세션 완료 시 한 번.** `PUT /sessions`. 오프라인이면 저장해뒀다 연결 시 전송 | 엔지니어링 블로그에 명시 |
| **WaniKani** | 문항당 한 요청. `POST /reviews`. 멱등성 키 없음 | 공개 API 문서 |
| **Anki** | 로컬 우선. `revlog.id` = **복습 시각(epoch ms)** → 클라이언트 생성 고유 id | DB 스키마 문서 |
| **Quizlet** | **불명.** 오프라인은 모바일 전용, 진행 상황 기기 간 동기화 안 됨만 확인 | 헬프센터 |

**Duolingo를 따른다.** 세션 단위 전송이 웹 테스트의 성격과 맞는다.

WaniKani는 반대 사례로 참고한다 — 문항마다 보내는데도 커뮤니티에
*복습 중 새로고침하면 진행이 날아간다*는 신고가 쌓여 있다.
**자주 보내는 것 자체가 유실을 막아주지는 않는다.**

> 주의: 이 주제로 검색하면 `/api/v1/sync` 같은 없는 엔드포인트를 지어낸
> AI 생성 글이 상위에 많이 뜬다. 위 표는 1차 자료만 추렸다.

## 3. 멱등성 — 이게 제일 중요하다

유실보다 **중복이 더 위험하다.**

같은 채점이 두 번 반영되면 SM-2가 망가진다. `good`이 두 번 먹히면 `repetitions`가
2 올라가고 간격이 실제보다 훨씬 길게 잡힌다. **그 단어는 한참 뒤에나 다시 나오고,
사용자는 이유를 모른다.**

네트워크가 불안하면 쉽게 생긴다 — 요청은 서버에 닿았는데 응답이 끊겨서
클라이언트가 실패로 알고 재전송하는 경우다.

그래서 채점 이벤트마다 **클라이언트가 만든 고유 id**를 붙이고, 서버는 이미 본 id를 무시한다.

```json
{ "id": "rv_01J8X...", "word_id": "w_1", "grade": "good", "reviewed_at": "..." }
```

Anki가 `revlog.id`에 복습 시각(밀리초)을 넣어 15년간 써온 방식과 같다.
두 기기의 기록을 합칠 때 같은 행을 다시 넣어도 아무 일이 안 일어나는 이유다.

표준화도 진행 중이다 — `Idempotency-Key` 헤더가 IETF 드래프트에 있고
(`draft-ietf-httpapi-idempotency-key-header-07`, 2025-10 갱신),
**UUID 권장 / 같은 키로 다른 내용을 보내면 안 됨**을 규정한다.

**멱등성이 확보되면 재전송이 안전해지고, 그 덕에 유실 대책이 단순해진다.**
아래 4절이 성립하는 전제다.

## 4. 유실 대책 — `sendBeacon` 하나면 된다

세션 도중 탭을 닫으면 메모리에 있던 채점이 날아간다. 25장 하고 닫으면 25장이 사라진다.

**탭을 떠날 때 `navigator.sendBeacon`으로 한 번 더 보낸다.** 페이지가 닫히는
순간에도 전송을 보장해주는 브라우저 기능이다. 3절 덕분에 중복 걱정 없이 쏠 수 있다.

### 넣지 않기로 한 것

| | 이유 |
|---|---|
| `localStorage`에 채점마다 저장 | Duolingo도 오프라인일 때만 저장한다. 웹은 오프라인 요구가 없다 |
| 5장마다 중간 전송 | 요청이 6배로 늘어난다. `sendBeacon`이 대부분의 이탈을 막는다 |

둘 다 **실제로 유실이 관찰되면** 그때 붙인다. 지금 넣으면 근거 없이 복잡해진다.

## 5. SM-2를 어디서 계산하나

| | 계산 위치 | 이유 |
|---|---|---|
| **앱** | 로컬 (Dart, [sm2.dart](../lib/data/srs/sm2.dart)) | **오프라인이 타협 불가.** 비행기에서 다음 카드가 뭔지 알아야 한다 |
| **웹** | **서버 (Python)** | 브라우저 편집기다. 오프라인 요구가 없다 |

Anki가 스케줄러를 클라이언트에 둔 것도 같은 이유다.

결과적으로 SM-2가 **Dart와 Python 두 곳**에 생긴다. 좋지 않지만,
**웹에 TS로 세 번째를 만드는 것보다는 낫다.** 서버 쪽이 생기면 앱도
온라인일 때는 그쪽을 쓰도록 옮겨 언젠가 한 벌로 줄일 여지가 남는다.

> 단어가 사용자 Drive로 갔다면 서버가 계산할 수 없어 이 설계가 무너진다.
> [TASKS.md](TASKS.md) 첫 줄에 **"구글 드라이브로 옮기는 계획은 접었다"**고
> 적혀 있어 문제없다. [DRIVE-PLAN.md](DRIVE-PLAN.md)는 폐기된 문서다.

## 6. API

### 6-1. 출제 — 이미 있다

[routes.py:138](../api/app/vocab/routes.py#L138). 그대로 쓴다.

```
GET /v1/review/due?limit=30      기본 50, 최대 200
```

### 6-2. 채점 — 새로 만든다

```
POST /v1/review/grades

{ "grades": [
    { "id": "rv_01J8X...", "word_id": "w_1", "grade": "good",  "reviewed_at": "2026-09-15T10:00:00Z" },
    { "id": "rv_01J8Y...", "word_id": "w_2", "grade": "again", "reviewed_at": "2026-09-15T10:00:07Z" }
]}

→ { "applied": 28, "skipped": 2 }     skipped = 이미 본 id
```

- `grade`는 `again` / `good` 두 가지 ([sm2.dart](../lib/data/srs/sm2.dart)의 `ReviewGrade`와 동일)
- 서버가 각 단어의 현재 `srs_*`를 읽어 SM-2를 돌리고 갱신한다
- 한 번에 받는 개수는 `sync/push`와 같이 **100건**으로 제한한다

### 6-3. `review_logs` 테이블

본 id를 기억할 곳이 필요하다. Anki의 `revlog`에 해당한다.

| 컬럼 | |
|---|---|
| `id` | 클라이언트 생성. **PK — 중복 삽입이 여기서 막힌다** |
| `user_id` · `word_id` | |
| `grade` | `again` / `good` |
| `reviewed_at` | 클라이언트 기준 채점 시각 |
| `created_at` | 서버 수신 시각 |

**부수 효과가 크다.** [TASKS.md:120-123](TASKS.md)의 통계 항목
(오늘 복습한 개수, 학습 단계별 분포, 오래 복습 안 한 단어)이
이 테이블만 있으면 전부 계산된다. 지금은 원본 기록이 없어서 못 만든다.

### 6-4. `sync/push`와의 관계

**별개 통로다.** `sync/push`는 *완성된 상태*를 통째로 받고,
`review/grades`는 *일어난 일*을 받는다. 앱은 계속 전자를, 웹은 후자를 쓴다.

## 8. 순서

1. `review_logs` 테이블 + 마이그레이션
2. 서버 SM-2 포팅 ([sm2.dart](../lib/data/srs/sm2.dart) → Python). **여기서 앱과 결과가 어긋나면 안 된다 — 테스트를 같이 짠다**
3. `POST /v1/review/grades`
4. 웹 세션 화면 + `sendBeacon`

**2번이 제일 위험하다.** 같은 단어를 앱과 웹에서 채점했을 때 다음 복습일이
달라지면 사용자가 바로 알아챈다.
