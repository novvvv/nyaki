# J-POP 유입 전략 · 저작권 구조

> 2026-08-06 논의 정리. 냐키(nyaki) 유입 채널로 J-POP/애니메이션 니치를 파고드는 전략과, 그 과정에서 저작권 리스크를 어떻게 격리할지에 대한 결론.
> 관련: [growth-v0.2.md](notes/product/growth-v0.2.md) · [pricing-v0.2.md](notes/product/pricing-v0.2.md)

## 왜 이 방향인가

**목표**: 포트폴리오 겸 수익화 (수익은 나면 좋은 정도)

범용 영단어 암기 앱은 레드오션이다. Anki가 무료로 SM-2를 제공하고 퀴즐렛·클래스카드 같은 것들이 무료 티어로 깔려 있는 상황에서, Pro가 파는 게 "동기화와 쿼터"라면 월 4,900원의 근거가 약하다. 사용자는 인프라에 돈을 내지 않는다.

반면 **"J팝/애니로 일본어 배우는 사람"**은 명확한 니치다.

- 가사에서 단어를 뽑아 바로 학습으로 넘어가는 흐름은 범용 단어장 앱이 못 따라온다
- 유입(콘텐츠) → 학습(앱) → 리텐션(SRS)이 한 줄로 이어진다
- 포트폴리오로도 "영단어 앱 만들었어요"보다 "특정 사용자층의 학습 흐름을 처음부터 끝까지 설계했어요"가 강하다

**유입 산수 참고**: 콘텐츠 유입 → 앱 설치 → 유료 전환은 단계마다 크게 깎인다. 무료 앱의 유료 전환은 통상 1~3%. 월 10만원이라도 벌려면 유료 20명 → 활성 1,000명 안팎 → 블로그·유튜브 트래픽 수만 단위가 필요하다. 수익을 주목적으로 잡으면 노동 대비 수지가 안 맞으므로, **포트폴리오·학습을 주목적으로 두고 수익은 부가로** 보는 게 맞다.

## 최종 구조 — 채널 분리로 리스크 격리

```
유튜브 채널  (가사 + 번역 영상 · 수익창출 OFF)
     │  링크
     ↓
블로그/웹사이트 (100% 자체 저작물: 단어·문법·해설·아티스트 정보)
     │  담기 버튼
     ↓
   냐키 앱 (단어장 · SM-2 복습)
```

**핵심 원칙**: 자체 도메인·애드센스·앱이 붙은 쪽에는 남의 저작물을 두지 않는다.

### 유튜브 쪽

- 가사·번역 영상은 여기에만 둔다
- **해당 영상은 수익창출 OFF**
- 음원은 Content ID가 자동으로 잡아 권리자에게 수익이 간다 → 권리자 입장에서 내릴 유인이 적음

### 블로그 쪽

- 곡 정보(아티스트·발매일·앨범·노래방 번호·차트 순위) — **사실 데이터라 저작권 대상 아님, 자유롭게 사용**
- 이 곡의 단어 N개 + 뜻 (→ 냐키 단어장 담기 버튼)
- 핵심 표현 3~5개 문법·뉘앙스 해설
- 원문 가사·MV는 **외부 링크** (유튜브/공식 가사 사이트)

## 저작권 판단 근거 (논의 정리)

### 왜 "가사 전문"을 자체 호스팅하지 않는가

집행은 소송이 아니라 **플랫폼 차단**으로 온다. JASRAC·한음저협은 개인을 고소하는 대신 호스팅·애드센스·앱스토어에 신고를 넣는다. 그러면 예고 없이 사이트가 내려가거나 애드센스 계정이 정지되고, **자체 제작한 부분까지 같이 죽는다.**

"나무위키·티스토리 블로그도 하는데?" → 합법이라서가 아니라 아직 문제 삼지 않은 것에 가깝다. 위키는 게시자가 불특정 다수라 책임이 흩어지고, 국내 포털 블로그는 플랫폼 차원의 라이선스 우산이 있을 수 있다(확인 필요). 자체 도메인 + 애드센스 + 앱 연동이면 "개인 블로그"가 아니라 **책임 주체가 명확한 사업자**로 보인다.

### 학습 자료와 가사 전문의 차이

저작권이 보호하는 건 **표현**이지 그 안의 사실·정보가 아니다.

| 안전한 쪽 | 위험한 쪽 |
|-----------|-----------|
| 곡에 나온 단어·문법·관용구 (언어의 공용 재산) | 가사 전문 게재 |
| 곡 메타데이터 (아티스트·발매일·노래방 번호) | 전곡 줄별 번역 |
| 한두 구절 인용 + 긴 해설 | 형식만 바꿔 전문을 재구성 가능한 자료 |
| 원문 순서와 무관하게 재구성한 단어장 | |

판단 기준은 "얼마나 가져왔나 / 원본을 대체할 수 있나". **자료 전체를 보고 원곡 가사를 복원할 수 있으면 이름표만 바꾼 셈**이다.

### 유튜브 리스크의 실제 모습

- 두 겹 권리: **음원(녹음물)**은 Content ID가 자동 정산 / **번역 가사**는 별개 권리라 Content ID가 안 잡고 묵인 상태
- 수익창출 OFF는 합법화가 아니라 "권리자가 움직일 유인을 줄이는" 효과
- 실질 제재는 채널 단위: Content ID 클레임(수익만 넘어감, 무해) → 지역 차단 → 저작권 경고(strike), **3회면 채널 삭제**
- 경고는 대개 한 번에 오지 않고 하나씩 온다. 90일 후 만료. 첫 경고 시 해당 레이블 곡을 빼는 식으로 대응할 시간이 있다
- 영상이 수익화된 블로그로 트래픽을 보내면 "비영리" 방어는 약해진다 — **"수익 안 내니까 괜찮다"를 근거로 삼지 말 것**

### 채널을 여러 개로 쪼개면?

경고는 채널 단위로 쌓이므로 한 채널이 삭제돼도 다른 채널이 자동으로 죽진 않는다. **다만 실효성이 낮다**:

- 구글은 계정 단위로도 본다. 반복적으로 같은 유형의 침해로 채널을 만들고 지우는 패턴은 "정책 우회"로 판단해 연결 채널까지 정지 가능
- 삭제된 채널 운영자가 새 채널을 파는 것 자체가 약관 위반
- 구독자·알고리즘 신뢰도가 쪼개져 성장 속도가 1/N로 떨어짐 → 유입 채널이라는 목적과 정면 충돌

**결론**: 채널 분산보다 (a) 민감한 권리자/레이블 파악해서 피하기 (b) 유튜브 밖 독립 유입 경로 확보가 실질적이다.

## 단일 실패점 주의

유튜브가 유일한 유입구면 채널이 막히는 날 트래픽이 0이 된다. 블로그 자체가 검색으로 독립 유입되는 콘텐츠(문법 정리, 표현 모음, 아티스트별 단어장)를 같이 쌓아둘 것.

## 기술 스택 · 프로젝트 구조

- **별도 Next.js 프로젝트** (nyaki 폴더 밖, 형제 폴더 + 새 레포)
  ```bash
  cd ~/Desktop && npx create-next-app@latest jpop-lyrics && cd jpop-lyrics && git init
  ```
- **별도 도메인** — 브랜드·SEO 주제 일관성 + 리스크 격리
- **백엔드**: 새 서버 살 필요 없음. 같은 Lightsail 인스턴스에서 Postgres 스키마/DB만 분리, FastAPI 프로세스 별도 기동. 곡 데이터는 자주 안 바뀌므로 Next.js가 빌드/ISR 시점에 DB 직접 읽는 방식도 가능
- **로그인**: nyaki와 **같은 Firebase 프로젝트** 사용 → UID가 같아 계정 연결 작업 없이 "가사 → 냐키 단어장 저장" 연동 가능
  - Firebase 콘솔 → Authentication → Authorized domains에 새 도메인 추가
  - 동일한 `NEXT_PUBLIC_FIREBASE_*` config 복사
  - 대부분의 방문자는 로그인 불필요 → 가사/학습 페이지는 완전 공개 (크롤러 접근 보장), 로그인은 단어 저장 시에만
- **URL 구조**: `/artist/[slug]`, `/artist/[slug]/[song-slug]`
- **데이터 모델 초안**: `Artist`, `Song`(제목 원어·로마자·한글, 발매일, 노래방 번호), `ChartSnapshot`(월간/연간 순위), `TourEvent`(내한 일정)

**왜 nyaki web에 안 붙이는가**: nyaki web은 로그인·설정 위주의 작은 앱이고 가사 사이트는 수천 페이지를 찍어내는 콘텐츠 사이트다. 빌드 시간·배포 주기·ISR 전략이 완전히 다르고, 한 도메인에 "단어 암기 앱"과 "J팝 가사"가 섞이면 SEO 주제 일관성도 떨어진다.
